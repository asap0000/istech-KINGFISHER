# 企画書 — PrivacyCamera 専用リポジトリへの切り出し

**種別**: 企画書（増分の記録）　|　**日付**: 2026-08-26　|　**起案**: istech Android チーム（PrivacyCamera 席）
**対象**: `asap0000/istech-KINGFISHER`（本リポジトリ・PUBLIC・Apache-2.0）

---

## 1. 何をしたか（3行）

1. PrivacyCamera を前身リポジトリ（`asap0000/HOMEPAGE` の `android/` 配下・社内ツール BusCourse と同居）から
   **専用リポジトリへスナップショットで切り出した**。
2. 同時に、**初回配布後には二度と変えられない 2 つ**を確定した——**applicationId**（`com.privacycamera` →
   `com.istech.privacycamera`）と、**リリース署名鍵**（DN に屋号 `O=istech / CN=istech` を焼き込み）。
3. 機械的担保（CI）を**全部持ってきた**。この製品の主張は「通信しない」であり、**それを保証しているのは
   人間のレビューではなく CI** なので、CI を置いてこないと商品の芯を置いてくることになる。

## 2. ネットワーククラスの自己判定（クラス制度 §7-1）

**判定＝コランダム（corundum）。** 機械可読宣言は
[`istech-class.yml`](../istech-class.yml)（リポジトリルート・制度定義 §7-2 の配置規約どおり）。

### 軸1（ネットワーク自由度）＝コランダム

制度定義 §7-1 のチェックを上から順に当てた結果、**最初の行で YES**：

> ネットワーク機能を持つコードが依存関係に一切ない → コランダム

- `AndroidManifest.xml` に `android.permission.INTERNET` の宣言が無い（**AAR 由来の注入も無い**——
  トパーズのように `tools:node="remove"` で除去しているのではなく、**そもそも注入元が依存ツリーに居ない**）。
- 依存はすべて AndroidX / Compose / CameraX / Biometric / coroutines。通信系ライブラリはゼロ。
- **allowlist を持たない**（allowlist はトパーズ以下の器。コランダムはブラックリスト方式）。

**前身リポジトリでの分類（制度定義 §8 の資産表「PrivacyCamera＝製品層・コランダム」）から変更なし。**
モジュール分割の実態も変わっていない——制度定義 §4c が前例として挙げていた
「`:app`（コランダム）と `:buscourse`（トパーズ）は同一リポジトリだがクラスは別」の**同居が解消され、
1 リポジトリ＝1 資産＝1 クラスになっただけ**である（切り分けの単位＝実行単位、という §4c の原則に沿う）。

### 機械的担保（制度定義 §3 のコランダム検査を、この 3 段で満たす）

| 検査 | 実体 | 落ちる条件 |
|---|---|---|
| ソース権限 grep | `android.yml` "Verify offline / no-share-intent / no-temp-file guarantees" | `AndroidManifest.xml` に INTERNET が現れた瞬間（数秒で落ちる。ビルドを待たない） |
| 出荷 APK の aapt 検査 | `android.yml` "Verify offline policy (no INTERNET permission)" / `release.yml` の同名ステップ | debug/release・lite/pro の**どの APK でも**マージ後マニフェストに INTERNET があれば |
| 依存ツリー検査 | `android.yml` "Verify offline policy (no network libraries)" | `liteRelease` / `proRelease` の RuntimeClasspath に okhttp・retrofit・ktor・volley・grpc・apache.http・cronet が現れたら |

加えて、この製品固有の 2 つ（提出用出力機能の仕様 P3/P4）も CI が固定している：
**`print/` 配下に共有インテント（`ACTION_SEND` / `FileProvider`）が現れたら落ちる**、
**`print/` 配下がアプリストレージにファイルを作ったら落ちる**（出力先は印刷フレームワークの
ファイルディスクリプタだけ、という設計を機械で固定している）。

見た目の退行は Roborazzi ＋自作 Bitmap ゴールデン（基準画像 5 枚）が固定する。

### 軸2（データ機微度・制度定義 §4b）

**PII を保有する**（免許証・保険証・マイナンバーカード・通帳＝この製品の存在理由そのもの）。
ただし**再識別鍵つきではない**——本アプリはマスク済みデータと原本を結びつける対応表・逆写像を
**外部に出さない**（原本もマスク版も同じ端末の同じ暗号化ストレージの中にあり、対応表という
概念自体が端末外に存在しない）。

制度定義 §4b-2 の `保護要件 = max(軸1の要求, 軸2の要求)` に対する充足：
軸2＝PII は「アイアン級の保護要件（認証情報の保管・要保護データを含む出力ファイルの置き場所・
平文保存の是非）を軸1と無関係に満たす」ことを求める。本アプリの充足は次のとおり。

- **平文保存の是非**: 原本は AES-256-GCM で暗号化。鍵は Android Keystore 内に生成され端末外へ取り出せない。
- **出力ファイルの置き場所**: アプリ専用内部ストレージ（`filesDir/secure/`）。`.nomedia` 設置でメディア
  スキャナ対象外。`allowBackup=false` ＋ `data_extraction_rules.xml` でクラウドバックアップ・端末間移行から除外。
- **端末の外へ出る経路は 3 つだけで、いずれも原本を出さない**: ①マスク版の書き出し ②パスフレーズ暗号化
  バックアップ（Pro・`.pcbak`） ③提出用印刷（マスク＋透かし焼き込み済みの複製のみ）。
- **⚠ 制度上の未決に触れている点**: 軸2 の台帳への書き方（`istech-class.yml` に `data_sensitivity:` を
  足すか別ファイルか）は**制度定義 §11 で未決・鍵の持ち主は官房**。よって `istech-class.yml` には
  **軸1 だけを書き、軸2 は本書に記述するに留めた**（未決のスキーマを現場で勝手に鋳造しない）。
  なお顧客向けバッジに出すのは軸1のみ（§4b-4）なので、販売準備は本判断で止まらない。

## 3. 移行の方式と、その理由

**方式＝スナップショット開始**（前身リポジトリから現在の内容をコピーして初コミット）。
`git filter-repo` による履歴の移送は**採らない**。

- **理由**: β期間の履歴は前身リポジトリに残っており、失われない。**原本を痩せさせない**方が調査の
  一次資料として健全で、履歴移送のコスト（サブモジュール・他モジュールと絡んだ再構成）に見合う
  対価がない。本リポジトリの `git log` は「商品としての PrivacyCamera」の履歴として、この初コミットから始まる。

### 移したもの / 移さなかったもの

| | 内容 |
|---|---|
| **移した** | `app/` 一式（ソース 38 ファイル・リソース・基準画像 5 枚）／Gradle 構成（wrapper・Version Catalog・`gradle.properties`）／**CI 3 本**（`android.yml`・`release.yml`・`record-goldens.yml`）／PrivacyCamera の仕様書・設計検討・実装計画・βテスト項目表（`docs/` 6 本＋索引）／アイコン原画 |
| **移さなかった** | `:buscourse` モジュール（社内ツール・トパーズ級・別資産）／`android/ci/offline-allowlist.yml`（トパーズの器。コランダムは持たない）／`.istech/` サブモジュール（社内の正典群）／**旧 release keystore**（旧 applicationId 用。後述）／**`PROJECT-STATUS.md`**（下記） |

**⚠ `PROJECT-STATUS.md` は公開しないことにした（独立レビューの指摘による）**。前身での開発引き継ぎ文書で、
**事業者の氏名・住所の出し方をどう扱うか、価格戦略、海賊版対策の有無、想定問答**といった社内の検討が
そのまま書かれていた。本名も住所も直接は書かれていないが、**「開発者は本名と自宅住所を出品情報から
隠そうとしている」と自ら公示するに等しく**、個人特定を試みる人間への手がかりになる。社内側に保全した。
**⇒ 代わりに [`docs/README.md`](README.md) を置き、どれが現行仕様でどれが経緯の記録かを外部読者に示した**
（失効した「未着手」表記などを、今の状態と読み違えないため）。

### 共有していた Gradle 設定の分離

- `settings.gradle.kts` から `include(":buscourse")` を削除。**リポジトリルート＝Gradle ルート**になったので、
  CI の `working-directory: android` と `android/` プレフィックスを全て外した（パスがひとつ浅くなった）。
- **Version Catalog を `:app` 専用に削いだ**——MapLibre（`android-sdk` / `plugin-annotation`）・okhttp・
  Room（`runtime` / `ktx` / `compiler` / `testing`）・WorkManager・DataStore・KSP・appcompat・material・
  `activity-ktx`・`lifecycle-service`・`coroutines-guava`・`coroutines-test` は `:buscourse` 専用だったので削除。
  **削除後、`:app` が参照する `libs.*` が全て catalog に存在し、catalog 側に未使用エントリが 1 つも無いことを確認済み。**
  **コランダムのリポジトリに okhttp のバージョン宣言が残っているのは、宣言と実態の食い違いとして良くない**
  （制度定義 §7-2 は宣言と検査結果の不一致をマージブロックとしている）。
- CI から `:buscourse` 向けステップ 4 本（ソースマニフェスト検査・出荷 APK 検査・Kotlin 版一致検査・
  ネットワークライブラリ allowlist 差分検査）を削除。**`:app` 向けの検査は 1 つも削っていない。**

## 4. 初回配布前にしかできない 2 件

### (A) applicationId の変更 — 実施済み

`com.privacycamera` → **`com.istech.privacycamera`**（namespace とパッケージディレクトリも同時に移動）。

- **`jp.istech` ではなく `com.istech`** を採った。理由＝兄弟モジュール（BusCourse）が既に
  `com.istech.buscourse` を使っており、**屋号配下の名前空間を揃える方が自然**だから。
- **フレーバーの suffix 構成は実態のまま維持**した：**Lite＝`com.istech.privacycamera.lite`
  （`applicationIdSuffix = ".lite"`）／Pro＝`com.istech.privacycamera`（suffix なし）**。
  Lite と Pro が別 ID なので同一端末に併存インストールできる、という性質は変わらない。
- **なぜ今しかできないか**: Android は「同じ applicationId かつ同じ署名鍵」でしか更新を許さない。
  一度でも配布した後に ID を変えると、既存ユーザーから見て**別アプリ**になり、更新経路が切れる。

> **⚠ 正確には「初回配布前」ではない**——前身リポジトリの GitHub Releases で **β版が配布済み**である
> （最新 `v0.4.0-beta`・2026-07-05）。したがって **β版を入れている端末から見ると、正式版は別アプリ**になる。
> 正式販売前の今なら切り替えてよい、というのが判断だが、**βテスターには案内が要る**（§6-5）。
> 幸い移行経路は製品機能として既にある——Pro は暗号化バックアップ（`.pcbak`）の書き出しと復元、
> Lite は Pro 移行用の書き出しを持つ。**旧アプリで書き出し → 新アプリで復元**が案内できる。
> ただし過去に「Lite→Pro 移行の取り込みが 0 件（原因＝旧インストールとのデータ非互換。クリーン導入で解消）」
> という前例がβ期間にあるので、**案内する前に実機で1往復通すこと**。
> **⚠ 端末内の暗号鍵も引き継がれない**——原本の暗号鍵は Android Keystore のアプリ単位エントリなので、
> **applicationId が変われば別エントリ**になる。β版のデータを新アプリから直接読む方法は存在せず、
> **救済経路はアンインストール前の書き出しだけ**である。README の入手欄にもこの警告を置いた。

**実射で確認済み**（2026-08-26）: ビルドした APK の実 ID が `com.istech.privacycamera.lite` /
`com.istech.privacycamera` であること、両方とも INTERNET 権限を要求しないことを `aapt dump` で確認。
テストは 5 suites / 27 tests / 0 failures、**skipped 0**——
すなわち**基準画像 5 枚は再ベースライン不要**だった（パッケージ名は描画結果に影響しないため。
「スキップされて緑」ではなく「実際に比較されて緑」であることを skipped 数で確かめている）。

### (B) リリース署名鍵の生成 — 実施済み

| 項目 | 値 |
|---|---|
| 別名 | `istech-privacycamera` |
| DN | **`CN=istech, O=istech, C=JP`**（屋号を焼き込み） |
| 鍵 | RSA 4096bit / SHA384withRSA / 有効期限 2056-08-18 |
| 証明書 SHA-256 | `1C:B6:01:C4:…:17:3A`（全桁は保管記録に） |

**署名の実射で検証済み**: この鍵で `assembleRelease` した Pro APK を `apksigner verify` にかけ、
`Signer #1 certificate DN: CN=istech, O=istech, C=JP` と v2 署名スキームの検証 OK を確認した。

- **旧鍵は持ち込んでいない**。旧鍵は旧 applicationId 向けであり、ID を変えた時点で更新経路の
  連続性という旧鍵の存在理由が消える。旧鍵は前身リポジトリに残置。

#### ★署名鍵はリポジトリに置かない（当初案からの変更・独立レビューの指摘による）

前身リポジトリは **GPG 対称暗号にした keystore を `app/release.keystore.gpg` としてコミットし、CI が
パスフレーズ（Secret）で復号する**方式だった。当初はこれを踏襲したが、**独立レビューの指摘を受けて取りやめた。**

- **理由**: **公開した暗号文は取り消せない。** fork・アーカイブ・第三者のクローンへ恒久的に複製され、
  **レート制限のないオフライン総当たりに永久に晒される**。攻撃者と署名鍵の間に立つのはパスフレーズ 1 枚だけ。
  鍵が破られたときの損害は「正規のアプリに上書きインストールできる APK を攻撃者が署名できる」——
  **プライバシー製品としては最悪の失陥**である。
- **⚠ 前身リポジトリも PUBLIC だった**（レビュー時の「非公開だろう」という推定は外れていた）。
  つまり**旧鍵の暗号文は既に公開されており、それは取り消せない**。だからこそ**新しい鍵では繰り返さない。**
  旧鍵の扱い（失効させるか・β版利用者への影響をどう見るか）は別途オーナー判断とする。
- **採った方式**: keystore そのものを Secret（`RELEASE_KEYSTORE_BASE64`）に置き、CI がビルド時に復元する。
  **公開される暗号文はゼロになる。** CI の変更はステップ 1 つの置き換えだけで、コストは増えていない。
- `.gitignore` に `*.gpg` / `*.base64` を追加し、**暗号化した形でも二度とコミットされない**ようにした。
- 鍵の保管は原本のほかに **2 系統**（①同一 PC の別物理ディスクへの固定コピー ②本リポジトリの
  `app/release.keystore.gpg`＝GPG 対称暗号・リモート）。**両系統とも SHA-256 の一致で検証済み。**
  詳細と復旧手順は社内の保管記録に置いた（**パスフレーズはリポジトリにもこの文書にも無い**）。
  - **⚠ 既存の日次バックアップに任せる案は実測で棄却した**——そのジョブは `/MAXAGE:4`（4 日以内に
    更新されたファイルのみ）で回っており、**更新されない署名鍵は 4 日を過ぎると新しい世代に入らない**。
    世代を整理した瞬間にバックアップが静かに消える。**世代管理の外に置くのが正しい。**
- **鍵を失うと、以後アップデートを配布する手段が永久に無くなる**（別 ID で出し直すしかなく、既存
  ユーザーの更新経路は切れる）。バックアップ 2 系統はそのための備えである。

## 5. Apache-2.0 の実務

- `LICENSE`（Apache-2.0 全文）／`NOTICE`（帰属表示）／`THIRD_PARTY_NOTICES.md`（第三者ライセンス一覧）。
- **全 Kotlin ソース 38 ファイルにライセンスヘッダを付与**した。
- **含意（了承の上で公開している）**: フルソース公開により、**誰でも Pro を自分でビルドできる**。
  BOOTH での 880 円は、**署名済みビルド・以後の更新・サポート**に対する対価というモデルである。
  ソースが読めることは、この製品の主張（「通信しない」）を**買う前に自分で確かめられる**という
  意味で、むしろ商品価値の側にある。

## 6. 残っている作業（本席の範囲外・オーナー作業）

1. **本リポジトリへの push**（外向きの不可逆操作＝オーナー専権）。
2. **GitHub Secrets の登録 3 件**（`RELEASE_KEYSTORE_BASE64` ＝ keystore そのもの /
   `RELEASE_STORE_PASSWORD` / `RELEASE_KEY_ALIAS`）。未登録の間、`android.yml` はリリース APK を
   未署名で出力し、`release.yml` は明示的に失敗する（**静かに未署名のまま配布される事故は起きない**）。
3. **BOOTH への出品操作**（オーナー専権）。
4. **LP の検証 URL の差し替え**——本リポジトリの `AndroidManifest.xml` 直リンクへ。
   **リンク切れの状態で LP を公開しない**ため、差し替えは push 後に行う。
   （LP 起草が想定しているパス `…/istech-KINGFISHER/blob/main/app/src/main/AndroidManifest.xml` は
   本リポジトリの実配置と一致している。push した時点で有効になる。）
5. **βテスターへの案内**（§4-A の注記）——正式版は別アプリになること、旧アプリで書き出してから
   新アプリで復元すること、**案内前に実機で移行を1往復通すこと**。
6. **前身リポジトリの Releases の扱い**——β版（`v0.1` 〜 `v0.4.0-beta`）は前身側に残っている。
   本リポジトリの Releases と二重に見えるので、前身側に「開発は本リポジトリへ移った」旨を
   1 行足すか、リリースを整理するかをオーナーが決める。
